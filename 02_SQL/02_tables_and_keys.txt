1)    Tables
        How relational databases actually store information — everything lives in tables
        • A table holds one type of thing (students, employees, branches)
        • Every table has two parts: columns and rows
        • Table = a grid where I store one kind of record

2)    Columns
        The vertical sections — each one defines a single attribute (piece of info) about the thing
        • Student table columns: student_id, name, major
        • Inside the name column sit the names of all students
        • Inside the major column sit the majors of all students
        • Column = one attribute, repeated down the whole table

3)    Rows
        The horizontal entries — each row is one actual record
        • One row in the student table = one student
        • That single row stores their ID, name and major together
        • Row = one entry / one real thing
        • Columns = what info I store, Rows = the actual things I stored it about

4)    Primary Key
        A special column that uniquely identifies each row in the table
        • Always underlined / marked when drawing the table
        • No two rows can share the same primary key
        • Can be anything — a number, a string of text, whatever I choose
        • Every table should have one
        • Primary Key = the attribute that tells rows apart, no matter what

5)    Why Primary Keys matter
        They let me tell apart rows that otherwise look identical
        • Two students both named Jack, both biology majors
        • Name is same, major is same — but student_id is different
        • So I refer to "student 1" and "student 4", not "Jack"
        • Watch out: without a primary key I have no way to point at one specific row

6)    Surrogate Key
        A primary key that means nothing in the real world — just a number I made up
        • Employee IDs like 100, 101, 102
        • Jan's ID is 100 — that 100 doesn't mean anything outside my database
        • Purely for identifying the row internally
        • Surrogate Key = made-up ID with no real-world meaning

7)    Natural Key
        A primary key that already exists and has meaning in the real world
        • Using employee SSN (Social Security Number) instead of employee_id
        • SSN already uniquely identifies a citizen outside the database
        • Natural Key = a real-world unique value used as the key
        • Both are just types of primary keys — difference is real-world mapping or not

8)    Foreign Key
        A column that stores the primary key of a row in another table — this is how I link tables
        • Marked in green / different colour when drawing
        • Employee table gets a branch_id column
        • That branch_id is the primary key over in the branch table
        • Jan's branch_id = 1 → branch 1 is Corporate → Jan works at Corporate
        • Michael's branch_id = 2 → branch 2 is Scranton
        • Foreign Key = a pointer to a row in another table

9)    Multiple Foreign Keys on one table
        One table can hold more than one foreign key
        • Branch table has mgr_id (manager ID) → points back to employee table
        • Scranton's mgr_id = 101 → employee 101 is Michael Scott → he manages Scranton
        • Stamford's mgr_id = 102 → Josh Porter manages Stamford
        • So employee points to branch, and branch points back to employee

10)    Self-referencing Foreign Key
        A foreign key that points back into its own table
        • Employee table gets super_id (supervisor ID)
        • Angela's employee_id = 103, her super_id = 101 → her supervisor is Michael Scott
        • Michael's super_id = 100 → his supervisor is Jan Levinson
        • Lets me define relationships between rows of the same table

11)    Composite Key
        A primary key made of two columns together, because neither one alone is unique
        • Branch_supplier table: branch_id + supplier_name
        • Hammer Mill appears twice (supplies branch 2 and branch 3) — not unique alone
        • branch_id 2 appears many times — not unique alone
        • Only the combination "Hammer Mill + branch 2" shows up once
        • Composite Key = two (or more) columns that are unique only when combined
        • Watch out: the same combination must never repeat

12)    Composite Key made of Foreign Keys
        A very common and useful pattern — both parts of the composite key point to other tables
        • Works_With table: emp_id + client_id + total_sales
        • emp_id is a foreign key → employee table
        • client_id is a foreign key → client table
        • Together they form the primary key
        • Employee 101 (Michael Scott) sold client 401 (Lackawana County) $267,000
        • Employee 104 (Andy Bernard) sold client 403 (John Daly Law) $5,000
        • Used to store info about the relationship itself, not just the link

13)    Putting it together — a company database
        Real schemas chain many tables through keys
        • employee → primary key + branch_id (FK) + super_id (FK)
        • branch → primary key + mgr_id (FK)
        • client → primary key + branch_id (FK)
        • branch_supplier → composite key
        • works_with → composite key of two foreign keys
        • The more complex the design, the more keys needed to hold it together

14)    Wrap Up
        • Relational databases store data in tables made of columns and rows
        • Columns = attributes, Rows = individual entries
        • Primary key uniquely identifies every row
        • Surrogate key has no real-world meaning, natural key does
        • Foreign key stores another table's primary key and creates the relationship
        • A table can have several foreign keys, even one pointing to itself
        • Composite key uses two columns together when one isn't enough
        • Keys are the whole mechanism for defining relationships between tables
